# Reactor

The engine. The platform.

Use the current execution references in this folder as source material:

- [Current action execution model](action-execution-model.md)
- [Action execution flows](action-execution-flow.md)

They describe v0/current behavior and may be stale as implementation changes. Keep useful details, but v1 should define the new core instead of preserving accidental current constraints.

- support for infinite tasks/duties: goals that never really complete, such as "stay in touch with my grandma" or "get fit"
- skill grouping!
	- this is very important
	- built-in stuff should be versioned btw
		- innate/say@0.1.0
		- core/say@0.1.0
		- pro/searchWeb@0.1.0
	- managed intelligence aliases/wrappers
		- simpler picker names such as `@pro/efficient` instead of exposing the exact current model, provider, version, and reasoning mode
		- aliases act like managed symlinks: `@pro/efficient` can point to Kimi K2.5 today, then K2.6 or another better fit tomorrow
		- aliases can be owned by orgs, e.g. `@pro/efficient`, `@openai/GPT:latest`, `@xai/Grok-fast:latest`
		- users should be able to pin exact models when they care, but default UX should prefer stable capability names
- version everything: tasks, skills, ...
	- `updateInstructions()` should compute and persist a git-style diff at write-time, then render that diff to humans and future AI context instead of only saying that a title/body changed
- live UI customization
	- Meseeks should let users select a running UI/component and ask the AI to change its appearance or behavior: bigger, smaller, different color, rounder, different interaction, etc.
	- MDX/component rendering should make the app surface directly customizable at runtime
	- reference: [Agentation](../../references/agentation.md)
- bi-rendering
	- important components/actions/skills should be able to render for humans and for AI
	- human rendering targets UI; AI rendering targets model context, Markdown, XML-ish structure, or `ModelMessage[]`
	- this overlaps with [JSX for AI](../../backlog/jsx-for-ai.mdx), but the Reactor framing is broader: rendering is part of the engine contract, not just action-history cleanup
	- references: [JSX prompts in practice](../../references/jsx-prompts-in-practice.md), [jsx-prompts](../../references/jsx-prompts.md), [Priompt](../../references/priompt.md), [mdx-prompt](../../references/mdx-prompt.md)
- external task interfaces
	- any task can request incoming email addresses; each received email becomes a message/action on that task
	- tasks can also have outgoing email addresses when they need to send email
	- the same primitive should support HTTP endpoints, webhooks, WebSocket streams, Telegram-style integrations, and future external systems
	- incoming external events become task messages/actions; the task loop/triggers decide whether reactions run and what happens next
	- task activity is the shared history of all actions taken by humans, AI, skills, and external systems on that task
- redesign our skills to prompt using `<xml>` tags
- `instruct()` should likely become `plan()`. I'm not sure about `task.instructions`; could be `task.plan` or simpy `task.description` or even `.body`.
- sharing skills
	- at least some basic importing/exporting support
	- skill marketplace/subscriptions
		- people can offer skills they have evolved over time
		- installed skill instructions are probably public/inspectable after install
		- because skills keep evolving, users can subscribe to a source and be notified when an update is available; their Pro can update for them when policy allows
		- skills can be free or paid
		- skill authors can proxy API keys and charge usage, with or without markup (or make it free)
		- first-party `@pro` skills can proxy services like Tavily so customers get useful defaults out of the box; if we charge exactly provider cost, the accounting still goes through energy
		- third-party skills may add markup for risk, scarcity, service quality, or business model reasons
- subtasks
	- I should be able to create and move freely, controlling reactions
- keep "magic rock" naming for fun
	- including the comment in the file
- energy as a first-class citizen
	- estimated cost should be "max theoretical cost"
		- based on maxOutputTokens, fixed costs, and so on
		- for a hard skill, should predict the cost for the sandbox config in use (timeout time, max RAM usage, etc)
	- the model should see the cost of each skill and preemptively suggest other paths that could require more energy
	- done() could have a mandatory confidence: 0-100 field (so we could trigger a continue)
	- doubleCheck() starting from X energy
		- when a done() call is made, run a doubleCheck() to accept/reject it
	- properly account reasoning tokens
	- variable hard-skill costs
- multi-provider
	- code sandbox
	- LLM/AI
	- storage
	- 💡 we could support "provider credits", like what we have with Daytona
		- this could also be very useful for accounting!
		- so we need "provider" as a primitive, and trace usage to it
- ETH deposits
	- simplest possible version: accept ETH deposits into the user/task wallet, not checkout-style payments
	- wallet balance then pays for models, sandboxes, storage, skills, and external providers through the same accounting layer
	- support for x402

- take ActionCtx only (not MutationCtx anymore)
