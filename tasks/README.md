# Meseeks Tasks

Task system reference for both public and private task files.

## Canonical Location

This document is the source of truth and lives at:

- `tasks/README.md`

If you are working with tasks, read this file first.

## Structure

Tasks live in two roots:

```text
tasks/                 # public tasks (git-tracked)
├── active/
├── backlog/
└── <any-status>/

private/tasks/         # private tasks (may contain sensitive info)
├── active/
├── backlog/
└── <any-status>/
```

The first directory segment under each root is the task `status`.
Status names are dynamic. Creating a new top-level folder creates a new status.

Task keys are source-prefixed to avoid collisions:

- `public:active/my-task`
- `private:active/my-task`

## File Types

- preferred: `.mdx`
- supported: `.md`
- tolerated: `.txt` and extensionless notes

## Frontmatter

Frontmatter is optional, but when present it should stay minimal:

```yaml
---
title: Human readable title
priority: critical | high | medium | low
tags: [security] # or [ux] or []
---
```

Do not add these keys to frontmatter:

- `id`
- `status`
- `created`
- `updated`
- `parent`
- `source`
- `source_id`
- `blocks`
- `blocked_by`

Those values are derived by the indexer from filesystem and file metadata.

## Derived Metadata Rules

The indexer derives:

- `id` from file path (`status/path/to/task`)
- `status` from the top-level status folder
- `created` from filesystem timestamps (`birthtime`, fallback `ctime`)
- `updated` from filesystem `mtime`
- `parent` from nearest ancestor `_index.*` task when present
- `source` from task root (`public` or `private`)

## Subtasks

Use `_index.*` to define a parent task in a directory.

Example:

```text
private/tasks/active/feature-x/
├── _index.mdx
├── part-a.mdx
└── part-b.mdx
```

Rules:

- child tasks inherit nearest ancestor `_index.*` as parent
- folders without `_index.*` are grouping only, not parent tasks

## Task Body Template

```mdx
# <Task Title>

## Context
<background>

## Objective
<clear measurable goal>

## Subtasks
- [ ] <first>

## Progress Log
### YYYY-MM-DD
- Task created

## Notes
<constraints and references>
```

## Index Build System

Indexes are generated by:

- `.config/generate-task-index.ts`

Commands:

- one-off build: `bun run build:tasks`
- watch mode: `bun run dev:config`

Generated files are written to:

- `private/tasks/.generated/tasks.meta.json`
- `private/tasks/.generated/tasks.lookup.json`
- `private/tasks/.generated/tasks.graph.json`
- `private/tasks/.generated/tasks.content.json`

## Organizer Notes

The Organizer app reads generated indexes; it does not rebuild them.
If indexes are stale, run `bun run build:tasks` (or keep the root watcher running).

## Agent Workflow

When an agent works on a task:

1. Read `tasks/README.md` first.
2. If it is a subtask, read parent `_index.*` chain from top to leaf.
3. Preserve structure and metadata conventions above.
4. Update progress log entries with dates.
