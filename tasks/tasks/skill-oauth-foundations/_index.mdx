# Skill OAuth foundations

Platform sign-in and skill OAuth are different systems.

Platform sign-in is for entering Meseeks itself. For now that means Google, and later maybe SIWE.

Skill OAuth is `skills-only`: the user is already signed in to Meseeks and then authorizes a third-party app so a skill can act on their behalf.

This task is about the `skills-only` system only. It should not assume that every OAuth provider is also a valid Meseeks sign-in method.

## Objective
Define and scaffold the first real `skills-only` OAuth foundation in Convex so a skill can require a user-owned linked app, starting with fixed-provider Twitter API v2 flow and explicitly excluding arbitrary user-defined OAuth endpoints from v1.

## Subtasks
- [ ] Define the first concrete schema for linked apps, pending authorization state, and token refresh metadata.
- [ ] Implement a fixed-provider registry for `skills-only` services, with Twitter API v2 as the first supported provider.
- [ ] Add the Convex HTTP callback and authorization bootstrap flow, including state validation and safe redirect-back behavior.
- [ ] Define how actions/skills pause when authorization is missing and resume once the required connection exists.
- [ ] Add token refresh and invalidation rules so expired or revoked linked apps fail predictably.
- [ ] Define the server-side token access path from Convex actions so skills can fetch provider access tokens without browser involvement.
- [ ] Decide the internal/domain naming for these records and UI surfaces; do not ship `ServiceConnection` as product wording.
- [ ] Document the v1 boundary: fixed-provider OAuth only; no arbitrary user-defined OAuth endpoints yet.

## Notes
Use [better-auth task](../better-auth/_index.md) as auth context, but keep this task opinionated and implementation-first.

Better Auth is acceptable here as token/account plumbing for fixed providers, but this task should not depend on Better Auth becoming the primary app sign-in model forever.

The first implementation should optimize for:
- one concrete provider
- one concrete happy path
- one concrete token refresh path
- one concrete pending-authorization resume path

Do not design the v1 schema around infinite user-provided provider configs. That is a later system.

Acceptance should include one end-to-end Twitter OAuth happy path, one expired-token refresh path, and one pending-authorization action-resume path.
