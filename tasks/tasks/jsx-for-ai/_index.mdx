# JSX for AI

Meseeks currently renders action history for LLM calls in `convex/magicRock.private.ts` with one generic string shape:

```xml
<date>...</date><skill>...</skill><status>...</status><result>...</result>
```

That generic renderer is too blunt. It treats every action as the same kind of prompt event, even though different skills have very different model-context needs. Some actions are user-visible conversation (`say`), some are private reasoning (`reason`), some are control flow (`iterate`, `instruct`, `compose`), some are data acquisition (`searchWeb`, `scrapeLink`, `valyu_search`), and some are artifacts (`render`).

The renderer also intentionally does not render raw action arguments. That is usually correct because args can duplicate child action payloads and explode context size. The concrete example is `compose -> render`: production data showed every sampled `render` action created by `compose` had `render.args.code` equal to the parent `compose` tool-call input. Rendering both parent tool calls and child args would duplicate large code payloads.

At the same time, never rendering args loses important semantic context. `render` is the clearest case: the LLM currently sees the transpiled `render.result.text`, not the source JSX in `render.args.code`. If `render` fails, the next LLM needs the failed source code plus the error to repair the component. The arg is not incidental metadata there; it is the source artifact.

We already started reducing obvious context noise by skipping empty successful `iterate` and `instruct` actions. Production data supported that:

- `instruct`: 2,470 successful production actions, all with empty `result.text`
- `iterate`: 11,781 successful production actions, all with empty `result.text`
- those empty successes rendered only loop-control metadata like `<skill>iterate</skill>`

The next step should not be another pile of `if (action.skillKey === ...)` checks in `renderAction`. The right architecture is a per-skill AI history component system, analogous to UI action components like `SayAction.tsx`, `AnalyzeAction.tsx`, and `SearchWebAction.tsx`, but targeting `ModelMessage[]` instead of React DOM.

The product vision from the discussion:

- UI action components render actions for humans.
- AI history components render actions for LLM context.
- Both are "components", but they are different render targets.
- AI history components should use JSX because JSX is the right syntax for nested structured output.
- AI history components must not use React DOM, React SSR, MDX rendering, or HTML semantics.
- The runtime should be a small custom JSX system that produces a typed prompt/history AST.
- Multi-message rendering should be supported because not every action maps cleanly to one message.
- Action aggregation should be a first-class extension point. Example: five sequential user actions editing the task could render as one row for humans and one compact event for AI.
- No hacky or cheaty solution. The design must fit Meseeks' action/skill architecture.

This task exists because "should we render args?" is the wrong question. The right question is: what is the canonical model-history representation of each skill action?

For `render`, `args.code` is canonical because it is the source artifact. For `compose`, the successful action is usually control flow and should disappear because the child `render` action represents the artifact. For `instruct` and `iterate`, empty success is loop plumbing and should disappear. For `searchWeb`, raw args are probably just `<query>`, while the result deserves structured rendering or compaction. For user-defined skills, the default should remain conservative: render result text, not args.

## Conversation Notes
The chat produced several durable decisions and observations that should guide implementation:

- User agreed with the take: "Build a proper model-history projection layer per skill."
- User's preferred mental model is component-style: just as the app has specific React components per skill for human UI, the AI should have per-skill JSX components for context rendering.
- User explicitly agreed this should be a custom thing, not React DOM.
- User liked multi-message rendering and called out aggregation as definitely useful.
- User gave the aggregation example: five sequential user actions editing a task could be rendered for both human UI and AI as a single row/event.
- The assistant's strongest recommendation was to build a custom JSX runtime with a typed AST and a renderer to `ModelMessage[]`, not to adopt a generic library wholesale.
- The first milestone should keep token cropping behavior boring and unchanged. Add component rendering first; add Priompt-style token-aware pruning later.
- The first implementation should be intentionally small: prove the runtime and component registry with `GenericActionHistory`, `InstructHistory`, `IterateHistory`, `ComposeHistory`, and `RenderHistory`.
- Do not render raw args globally. A history component may select a specific arg only when that arg is the semantic artifact for the skill.
- Do not use Microsoft-owned prompt TSX libraries.

## Production Evidence
A read-only Convex production export was used during the discussion to inspect action history patterns. The export covered 40,658 actions from 2025-04-30 through 2026-04-27.

Empty successful control-flow actions:

- `instruct`: 2,801 total actions, 2,470 succeeded, zero successful actions had `result.text`
- `iterate`: 13,278 total actions, 11,781 succeeded, zero successful actions had `result.text`
- Empty successful `instruct` and `iterate` actions rendered as pure metadata like `<skill>instruct</skill>` or `<skill>iterate</skill>` with no useful payload.

`instruct` details:

- Most successful `instruct` actions reacted with `updateInstructions`.
- Other reactions included `iterate`, `askForClarification`, `say`, `scrapeTweet`, and `discard`.
- `action_details` showed many rendered `<skill>instruct</skill>` history messages across LLM calls, creating repeated context clutter.

`compose -> render` details:

- 298 production `compose` actions were observed.
- 225 `render` actions were created by `compose`.
- Every sampled `render` action from `compose` had `render.args.code === compose.action_details.llm.toolCalls[0].input.code`.
- Total `render.args.code` characters for compose-created renders: 2,285,458.
- Average `render.args.code` length: about 10,158 characters.
- Average `render.result.text` length: about 10,431 characters.
- Rendering parent compose tool calls, child render args, and child render results together would often triple-count the same artifact.

This evidence supports a semantic renderer:

- Omit empty successful control-flow actions.
- Render `render` source once, through `RenderHistory`.
- Do not render parent soft-skill tool calls and child action args together unless a dedupe/aggregation layer owns that choice.

Relevant prior research:

- JSX prompts in practice
  - Small signal that JSX prompt construction is useful in real product work.
- [jsx-prompts](https://fables.gg/blog/introducing-jsx-prompts-build-complex-prompts-for-llms-with-jsx)
  - Useful for the structured-data-to-Markdown part of AI rendering.
- [Priompt](https://github.com/anysphere/priompt)
  - JSX prompt tree, priorities, fallbacks, token budgeting, message components, source maps.
  - Useful ideas to borrow, but do not adopt wholesale before proving a smaller local runtime.
  - Best idea to copy: prompt/context as a tree that can be pruned intentionally under a token budget.
  - Warning to preserve: adding priorities everywhere becomes an anti-pattern and can hurt prompt cache stability.
- [mdx-prompt](https://github.com/edspencer/mdx-prompt)
  - Useful for the prompt-definition plus orchestrator pattern.
  - Not a fit for Convex action history because it uses MDX/React-style rendering and weaker dynamic data typing.
- react-prompt-kit: https://github.com/chatbotkit/react-prompt-kit
  - Useful escaping and XML prompt component ideas.
  - Do not use directly; React runtime is the wrong abstraction here.
  - Borrow the code-fence escaping and XML/tag injection lessons.
- Dotprompt: https://github.com/google/dotprompt
  - Useful later for versioned authored prompts, not dynamic action history.
  - Could fit soft-skill prompt definitions in the future.
- AI SDK `ModelMessage`: https://ai-sdk.dev/docs/reference/ai-sdk-core/model-message
  - This remains the final boundary that `askMagicRock` sends to model providers.

## Objective
Create a first-class AI history rendering layer where each skill can define its model-facing representation through custom JSX components. The layer must:

- preserve current generic history behavior for skills without a custom renderer
- allow specific skills to omit, compact, or restructure history without global hacks
- render `render` actions from semantic source code (`args.code`) instead of treating every arg as generic prompt content
- keep raw action args out of model context by default
- support future multi-message rendering and action aggregation
- keep the final output compatible with AI SDK `ModelMessage[]`

The end state should let us write something conceptually like:

```tsx
export function RenderHistory({ action }: ActionHistoryProps) {
	//
	const args = renderActionArgsSchema.safeParse(action.args);
	if (!args.success) return <GenericActionHistory action={action} />;

	return (
		<Message role="assistant">
			<Action skill="render" status={action.status} date={action._creationTime}>
				{action.status === 'failed' && <Error>{action.result.text}</Error>}
				<Source language="jsx">{args.data.code}</Source>
			</Action>
		</Message>
	);
}
```

That example is illustrative, not a final API commitment. The architectural point is that per-skill components decide the model-facing semantic representation.

## Design Principles
- Treat AI history rendering as a first-class render target, not a string helper.
- Keep action storage unchanged unless there is a proven need for persisted projections later.
- Keep args as raw storage by default; never promote all args into context automatically.
- Use Zod at every skill-specific boundary where args/results are interpreted.
- Prefer explicit per-skill components over generic inference from arg names.
- Preserve existing generic behavior for unknown/custom skills.
- Keep the first milestone small enough to review: runtime, registry, core components, tests.
- Add token-aware pruning and action aggregation after the baseline renderer is correct.
- Make escaping boring and reliable. Generated tags are trusted; text children are escaped.
- Avoid runtime magic that makes model context hard to debug.

## Proposed Architecture
The pipeline should become:

```text
actions
  -> group into history events
  -> render each event with AI history components
  -> serialize history AST into ModelMessage[]
  -> crop/degrade to token budget
  -> askMagicRock(...)
```

First milestone:

```text
actions
  -> one action = one history event
  -> render with AI history component registry
  -> serialize to ModelMessage[]
  -> existing cropHistoryToTokenLimit(...)
```

Later milestone:

```text
actions
  -> group sequential edits and reaction chains
  -> render groups/events with components
  -> apply density/pruning/full-summary-omit fallbacks
  -> serialize to ModelMessage[]
```

Suggested files:

```text
convex/action/history/
├── index.ts
├── renderActionHistory.tsx
├── renderHistoryNode.ts
├── types.ts
├── jsx/
│   ├── jsx-runtime.ts
│   └── types.d.ts
└── components/
    ├── GenericActionHistory.tsx
    ├── InstructHistory.tsx
    ├── IterateHistory.tsx
    ├── ComposeHistory.tsx
    ├── RenderHistory.tsx
    └── index.ts
```

Naming can change, but keep the separation clear:

- JSX runtime primitives
- render result/types
- per-skill components
- registry/lookup
- serialization to `ModelMessage[]`

## Runtime Shape
Use TypeScript automatic JSX with a per-file pragma:

```tsx
/** @jsxImportSource convex/action/history/jsx */
```

This avoids a global `tsconfig` change and lets React UI files keep using React's JSX runtime.

The custom runtime should implement:

```ts
export const Fragment = Symbol('HistoryFragment');

export function jsx(type, props, key) {
	return createHistoryElement(type, props, key);
}

export const jsxs = jsx;
```

Use a typed AST similar to:

```ts
type HistoryNode =
	| string
	| number
	| null
	| false
	| HistoryElement
	| Array<HistoryNode>;

type HistoryElement = {
	type: string | HistoryComponent;
	props: Record<string, unknown>;
	children: Array<HistoryNode>;
};
```

Avoid unsafe escape hatches. If a generic `Record<string, unknown>` is needed at the JSX boundary, narrow it immediately in component/render functions.

## Message Rendering Contract
The renderer should support omit, one message, and multiple messages:

```ts
type ActionHistoryRender =
	| { kind: 'omit' }
	| { kind: 'message'; role: 'user' | 'assistant'; content: HistoryNode }
	| { kind: 'messages'; messages: Array<{ role: 'user' | 'assistant'; content: HistoryNode }> };
```

The exact type can change, but it must represent these cases because:

- empty control-flow actions need omission
- normal actions usually render as one message
- future grouped events or tool-call/result pairs may render as multiple messages

Final serialization must produce `Array<ModelMessage>`.

## Initial Components
`GenericActionHistory`:

- current generic behavior
- date, skill, status, result text when present
- no args
- escaped text children
- fallback for unknown/custom skills

`IterateHistory`:

- omit empty successful `iterate`
- generic fallback for failures, skipped actions, pending authorization, and future text-bearing results

`InstructHistory`:

- omit empty successful `instruct`
- generic fallback otherwise

`ComposeHistory`:

- omit empty successful `compose`
- generic fallback otherwise
- do not render parent compose tool-call input in the first milestone

`RenderHistory`:

- parse `args.code` with Zod
- render source JSX as the canonical payload
- on failure, render both error text and source JSX
- do not make transpiled `result.text` the primary history payload
- if args are malformed, warn and fall back to generic rendering

## Future Components
Likely next targets after the first milestone:

- `UpdateInstructionsHistory`
  - compactly render which fields were updated
  - do not repeat full instructions when `{{task}}` already includes current task state
- `SayHistory`
  - render message text once; avoid duplicating `args.message` and `result.text`
- `ReasonHistory`
  - preserve useful private reasoning, but consider density modes for older reasoning
- `SearchWebHistory`
  - render query and structured/compact result
- `ScrapeLinkHistory`
  - render URL/title/summary first; full content only in high-density contexts
- `ValyuSearchHistory`
  - render query and compact findings; avoid dumping massive raw JSON forever
- lifecycle actions (`done`, `resolve`, `discard`, `stop`, `reopen`)
  - decide whether empty success should omit or compactly render a lifecycle marker

## Action Grouping
Do not overbuild grouping in the first pass, but design the API so it can exist.

Initial event type:

```ts
type HistoryEvent =
	| { kind: 'action'; action: Doc<'actions'> }
	| {
			kind: 'action-group';
			actions: Array<Doc<'actions'>>;
			reason: 'sequential-user-edits' | 'reaction-chain';
		};
```

First milestone can return one `HistoryEvent` per action.

Later grouping examples:

- five sequential user edits to task title/instructions/summary render as one `TaskEditedHistory`
- `compose -> render -> iterate` renders as one composition event or only the final artifact-bearing render
- `instruct -> updateInstructions -> iterate` renders as one task-planning event
- repeated budget/lifecycle actions compact into a single status event

The grouping rules should be shared or shareable with human UI aggregation later. The renderers should differ, but the event grouping concept can be common.

## Token Budgeting Direction
Keep current `cropHistoryToTokenLimit` behavior for milestone one.

Longer term, borrow Priompt's useful idea: context as a tree that can degrade under a token budget.

Preferred future density model:

```text
full -> compact -> summary -> omit
```

Examples:

- recent failed `render`: keep source + error at high priority
- old `scrapeLink`: keep URL/title/summary, drop full markdown
- old `searchWeb`: keep query + compact answer, drop raw result details
- old reasoning: summary or omit depending on task state

Avoid adding priority attributes everywhere. Priorities should be rare and deliberate. Too much priority metadata makes prompts unstable and harder to cache/debug.

## Escaping And Injection Rules
Implement escaping as part of the renderer, not per component.

Rules:

- generated tags from components are trusted
- text children are escaped
- code/source children are wrapped so they cannot break surrounding structure
- markdown/code fences must use dynamic fence length when needed
- arbitrary objects should only be rendered through explicit components like `<Json>` with size limits
- raw action args must never be stringified by default

This is model-context safety, not browser XSS, but malformed prompt structure still matters.

## Rejected Approaches
- Do not keep adding skill-specific `if` blocks in `convex/magicRock.private.ts`.
- Do not render all args globally.
- Do not use React DOM or `renderToStaticMarkup`.
- Do not use MDX prompt rendering for dynamic action history.
- Do not adopt Priompt wholesale in the first milestone.
- Do not make DB-configurable history rendering the first implementation.
- Do not render parent soft-skill tool calls and child action args together without a real dedupe/aggregation layer.

## Acceptance Criteria
- `convex/magicRock.private.ts` no longer owns per-skill history special cases directly.
- There is a custom JSX runtime for AI history that does not import React.
- At least `GenericActionHistory`, `IterateHistory`, `InstructHistory`, `ComposeHistory`, and `RenderHistory` exist.
- The default renderer does not render raw args.
- `render` model history uses source JSX from `args.code` and includes failure details when relevant.
- Empty successful `iterate`, `instruct`, and `compose` actions do not appear in model history.
- Existing unknown/custom skill history still renders result text as before.
- The resulting history is still `ModelMessage[]` accepted by AI SDK calls.
- The first milestone preserves existing token cropping behavior.
- There is an explicit event/grouping seam even if grouping behavior remains one action per event.
- Text escaping prevents user-controlled result/source text from breaking generated XML-ish structure.
- `bun typecheck` passes.
- Targeted tests for the renderer pass.
