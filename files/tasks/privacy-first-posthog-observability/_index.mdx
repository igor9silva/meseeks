# Privacy-first PostHog observability

Current observability is split across weak or noisy tooling:

- the old Vercel product analytics package, `<Analytics />` mount, and scattered `track()` calls have been removed from the app.
- the old Vercel Analytics event stream is not part of the product model anymore; product events are ledger rows such as actions, action details, file revisions, provider events, and transactions.
- Vercel Speed Insights still exists as performance telemetry. It is separate from product-event analytics and should get its own keep/remove decision.
- Sentry exists today, but the current setup is noisy and low-trust: dev activity leaks into notifications, handled problems are counted like real failures, and the instrumentation quality is not good enough to judge the tool fairly yet.
- the next step is **hosted PostHog**, not self-hosted PostHog.
- privacy is a hard constraint: use as much of PostHog as is actually useful, but do it intentionally instead of defaulting into creepy full-capture sludge.
- old monitoring work is now folded into this task: dev/develop failures should not page us, expected handled product errors should remain observable but non-urgent, severity semantics should be explicit, and anomalies should be counted without becoming fake incidents.

Current in-repo touchpoints already known from the scan:

- Speed Insights app shell mount: `src/routes/__root.tsx`
- client error/replay init: `src/client.tsx`
- build/release upload config: `vite.config.ts`
- Speed Insights package/dependency surface: `package.json`
- privacy copy that still names Vercel Analytics: `public/static/privacy-policy.md`

The repo scan undercounted Sentry scope once already. Treat "Sentry is client-only" as false unless a fresh rollout audit proves otherwise.

## Objective
Make PostHog the primary observability stack for Meseeks with privacy-first defaults, keep product events aligned with the durable ledger model, clean up bad instrumentation patterns that create fake signal, and leave a concrete keep-or-remove decision for Sentry based on real signal quality instead of vibes.

## Subtasks
- [ ] Inventory the real observability surface before swapping vendors:
  - confirm every current Sentry integration path in code, build, deploy config, and provider-side setup
  - classify current signals into product analytics, replay, performance, and actual error reporting
  - separate true failures from handled/user-facing states that should not page anyone
  - produce a numbered current-state report so follow-up fixes can be referenced by index
- [ ] Design the privacy-first PostHog baseline:
  - use **hosted** PostHog
  - decide and document the policy for consent, cookieless/cookie usage, user identification, session retention, replay masking, and autocapture scope
  - explicitly choose which PostHog capabilities are in scope now: pageviews, custom events, session replay, feature flags, error tracking, and any other actually useful surface
- [ ] Fix instrumentation quality before or during migration:
  - move analytics/event emission out of render paths into route lifecycle or event handlers
  - define one app-owned analytics/observability entrypoint instead of vendor calls scattered through routes
  - distinguish expected handled failures from reportable exceptions so noisy "errors" stop polluting alerts
- [x] Remove the old Vercel product analytics wiring:
  - removed `<Analytics />` from `src/routes/__root.tsx`
  - removed old Vercel product analytics imports/usages from route/component call sites
  - removed the old Vercel product analytics package from `package.json`
  - kept `@vercel/speed-insights` as separate performance telemetry, not product-event analytics
- [ ] Decide the Speed Insights boundary:
  - decide whether `@vercel/speed-insights` stays as lightweight performance telemetry
  - if it stays, document why it is not product analytics and what it is allowed to collect
  - if it goes, remove the package and app-shell mount in one pass
- [ ] Roll out PostHog as primary observability:
  - initialize PostHog in the client with privacy-preserving defaults
  - migrate existing product events to PostHog and dedupe route/page tracking
  - add replay/error configuration only after masking and noise rules are explicit
  - verify local/dev behavior does not contaminate production reporting
- [ ] Resolve Sentry explicitly instead of letting it rot:
  - either remove Sentry after PostHog signal is good enough
  - or keep a narrowed temporary Sentry setup with a documented reason, reduced scope, and cleaned-up alert semantics
  - in either case, stop the current dev-noise and handled-error spam
  - enforce severity semantics across Sentry/logs: `debug` for debug sessions, `info` for default visible logs, `warning` for admin notification, and `error` for urgent admin notification
  - add non-paging counters for unexpected-but-handled anomalies, such as tool calls present with finish reason `stop`
  - if Sentry stays, use the TanStack Start integration docs as the implementation reference: https://docs.sentry.io/platforms/javascript/guides/tanstackstart-react/
- [ ] Update user-facing/privacy documentation:
  - replace Vercel Analytics references in `public/static/privacy-policy.md`
  - document the actual PostHog data policy shipped in code
  - make replay/error capture language match reality
- [ ] Verify the rollout with concrete checks:
  - no old Vercel product analytics imports remain
  - route/page events no longer fire from render
  - production-only reporting rules are explicit and tested manually
  - event names and properties have one documented source of truth

## Notes
- Do not treat this as a blind vendor swap. Bad instrumentation is the first bug.
- The old Vercel product analytics package is already removed. Do not reintroduce a no-op analytics wrapper or a second product-event stream.
- Axiom supports monitoring AI SDK directly: https://x.com/njpatel/status/1970217382955360417
- If PostHog feature flags or experiments are added, do it only after the analytics/replay/error baseline is stable. Do not turn this into a kitchen-sink rollout on day one.
- Preserve rejected assumptions from this planning pass:
  - self-hosted PostHog is not the current plan
  - "Sentry is only client-side" is not a safe assumption
  - Vercel Analytics should not be used as the benchmark for what "working analytics" looks like
- Original monitoring example to preserve as non-urgent signal: `(xai/grok-4.1-fast-non-reasoning) has tool calls but finish reason is 'stop': cancelSchedule`.
