# Add MDXEditor to app MDX editing

The editor direction comes from the MDX editor architecture conversation embedded at the bottom of this task.

The decision from that conversation: Meseeks wants an MDX editor, not a generic rich text editor. MDX stays canonical. The first implementation spike should use MDXEditor for WYSIWYG editing because it already handles Markdown/MDX import/export and JSX plugin descriptors. Source editing can use MDXEditor's source/diff path if needed.

The app already stores and renders MDX-like task content:

- `schemas/taskSchema.tsx` describes task `instructions` as MDX-capable content.
- `src/components/TaskDetail.tsx` renders task instructions through `src/components/ui/mdx.tsx`.
- `src/components/EditableContent.tsx` currently edits task instructions with a plain multiline `Textarea`.
- `src/components/ActionComposer/ActionComposer.tsx` is the other primary long-form writing surface to evaluate.

The component model should be practical: known safe MDX JSX components may render as actual app components in the editor; unknown, dynamic, or unsafe JSX must remain literal/source-only content so it is not dropped, normalized into invalid MDX, or executed unsafely.

The `jsx live` fenced-code examples in MDXEditor docs are Sandpack/code-example behavior, not the persisted app component format. Meseeks app components should stay real MDX JSX where possible.

## Objective
Replace plain textarea editing for root app MDX content with a reusable Meseeks MDXEditor integration, starting with task instructions and then expanding only to other app surfaces confirmed to be MDX-editable.

Acceptance criteria:

- task plan/instructions can be edited with MDXEditor and still save exactly as MDX through the existing task update path.
- the action composer supports composing MDX content without losing existing submit, queue, voice transcription, shortcut, and draft/search-state behavior.
- every root app user-editable MDX field found by repo-wide inventory is either migrated to the MDX editor or explicitly documented as out of scope with a reason.
- non-MDX fields such as task titles still use the lightweight plain text editing path.
- existing MDX rendering through `src/components/ui/mdx.tsx` remains compatible with saved editor output.
- known safe JSX components can be represented through MDXEditor `jsxPlugin` descriptors when useful.
- unknown, dynamic, or unsafe MDX/JSX is preserved as source text/source-only content instead of being rendered through unsafe runtime evaluation.
- verification includes `bun typecheck`, `bun run build:tasks`, and a browser check of task instructions plus composer editing.

- [ ] Add the MDXEditor dependency and a single app-owned wrapper component for editable MDX content. Keep the wrapper narrow; do not make `EditableContent` pull MDXEditor into task titles or other plain text uses.

## Use 3 component classes

| MDX component type | Lexical representation | Example |
|---|---|---|
| **Void component** | `DecoratorNode` | `<Chart />`, `<Video />`, `<ToolResult />` |
| **Container component** | `ElementNode` + NodeState | `<Callout>children</Callout>` |

Lexical docs explicitly split extensible node types into `ElementNode`, `TextNode`, and `DecoratorNode`; `ElementNode` is for parent/container behavior, while `DecoratorNode` is for arbitrary rendered views/components. Source mentioned: https://lexical.dev/docs/concepts/nodes

## The key idea

Build a **typed MDX component registry**.

```ts
type MdxComponentSpec<Props> = {
	name: string;
	kind: "void" | "container" | "inline" | "raw";

	propsSchema: z.ZodType<Props>;

	EditorView: React.ComponentType<{
		props: Props;
		selected: boolean;
		updateProps: (patch: Partial<Props>) => void;
	}>;

	PreviewView: React.ComponentType<Props>;

	fromMdx: (node: MdxJsxNode) => Props;
	toMdx: (props: Props, children?: string) => MdxJsxNode;
};
```

Then every component is registered once:

```ts
const components = {
	Callout: {
		name: "Callout",
		kind: "container",
		propsSchema: z.object({
			type: z.enum(["info", "warning", "success"]),
			title: z.string().optional(),
		}),
		EditorView: CalloutEditorChrome,
		PreviewView: Callout,
	},

	Act: {
		name: "Act",
		kind: "container",
		propsSchema: z.object({

			id: z.string(),
		}),
		EditorView: ChartEditorCard,
		PreviewView: Chart,
	},
} satisfies Record<string, MdxComponentSpec<any>>;

## Important part

### Void component

Use `DecoratorNode`.

Good:

```mdx
<Chart id="revenue" />
```

Lexical:

```ts
class MdxVoidComponentNode extends DecoratorNode<React.ReactNode> {
	// state: { name: "Chart", props: {...} }

	decorate() {
		return <ComponentCard name={name} props={props} />;
	}
}
```

This matches Lexical’s model: `DecoratorNode` can render arbitrary React/other framework views through `decorate()`. Source mentioned: https://lexical.dev/docs/concepts/nodes

### Container component

Use `ElementNode`, **not** `DecoratorNode`.

Good:

```mdx
<Callout type="warning">
	Do not ship before Stripe is tested.
</Callout>
```

Lexical shape:

```txt
MdxContainerComponentNode(Callout, props)
	ParagraphNode
		TextNode
```

The children stay native Lexical content, so selection, editing, undo, keyboard movement, copy/paste, etc. are sane.

Use `NodeState` for props:

```ts
const componentNameState = createState("componentName", {
	parse: (v) => typeof v === "string" ? v : "",
});

const componentPropsState = createState("componentProps", {
	parse: (v) => isPlainJsonObject(v) ? v : {},
});
```

NodeState is designed for arbitrary node state with JSON serialization/history/reconciliation support, and reduces custom serialization boilerplate. Source mentioned: https://lexical.dev/docs/concepts/node-state

	name: 'Callout',
	kind: 'flow',
	props: [
		{ name: 'type', type: 'string' },
		{ name: 'title', type: 'string' }
	],
	hasChildren: true,
	Editor: CalloutMdxEditor
}
```

Then render the **actual component**:

```tsx
function CalloutMdxEditor({ mdastNode }: JsxEditorProps) {
	const props = mdastPropsToReactProps(mdastNode.attributes)

	return (
		<Callout {...props}>
			<NestedLexicalEditor
				block
				getContent={(node) => node.children}
				getUpdatedMdastNode={(node, children) => ({
					...node,
					children
				})}
			/>
		</Callout>
	)
}
```

That gives you:

```mdx
<Callout type="warning">
	Editable **markdown** inside.
</Callout>
```

rendered as the real `<Callout />`.

For unknown/dynamic components:

```mdx
<Component value={someRuntimeThing()} />
```

render as literal text/code-ish MDX, not as a broken fake component.

## MDXEditor vs TipTap vs raw Lexical

| Criterion | MDXEditor | TipTap custom | Raw Lexical custom |
|---|---:|---:|---:|
| MDX parsing/serialization | **Best** | You build it | You build it |
| WYSIWYG Markdown | **Best out of box** | Good, custom work | Lots of work |
| Actual React component rendering | Good | **Best** | Possible, but awkward |
| Editable children inside components | Good via nested editor | **Best via NodeViewContent** | Custom/awkward |
| Source mode | Built-in CodeMirror | You build | You build |
| Monaco source mode | External integration | External integration | External integration |
| Control over editor model | Medium | High | Highest |
| Time-to-good-product | **Best** | Medium | Worst |
| Risk | Medium | Medium-high | High |

## Updated preference

### 1. **MDXEditor**

Best first choice now.

Use it if:

```txt
You want a real MDX editor more than a generic rich-text framework.
```

Main reason: it already solved the hard boring layer — Markdown/MDX ⇄ editor state.

### 2. **TipTap**

Fallback if MDXEditor’s JSX component editing feels too boxed in.

TipTap is still better if the editor experience around custom components becomes the whole product. Its React NodeViews are a cleaner mental model for “render actual component with editable children”.

### 3. **Raw Lexical**

I would not do this anymore.

MDXEditor already gives you the Lexical-based MDX path. Going raw Lexical means rebuilding what MDXEditor exists to provide.

## Caveats

MDXEditor source mode is **CodeMirror**, not Monaco. The diff/source plugin supports source editing and CodeMirror extensions, but if you want a real pro editor, keep Monaco as your own separate source tab. Source mentioned: https://mdxeditor.dev/editor/docs/diff-source

Also, MDXEditor is client-side only in Next.js; their docs explicitly require disabling SSR for the editor. Source mentioned: https://mdxeditor.dev/editor/docs/getting-started

## Verdict

Use:

```txt
MDXEditor for WYSIWYG
Monaco for source
MDX as canonical source
Custom jsxPlugin descriptors for real components
Raw-text fallback for unsupported JSX
```

I’d only go back to TipTap if MDXEditor fails specifically on **component UX quality**, not because of MDX support.
